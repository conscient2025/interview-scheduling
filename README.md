# 浙江大学粤语社纳新面试排班

本仓库用于维护浙江大学粤语社纳新面试的结构化数据、自动排班规则和本地 XLSX 生成脚本。它解决的核心问题是：每次收到一份包含历史记录的最新报名表后，自动识别新增或改过时间的报名者，在尽量满足所有人可用时间的前提下重新整理分组，并把经过校验的精简数据直接同步到私有 GitHub 仓库的 `main` 分支。

> **隐私提示：**本仓库必须始终保持私有。仓库获准保存报名者姓名、学号和排班所需字段，但不得上传原始报名表、生成的排班 XLSX、联系方式、专业、部门志愿或其他问卷回答。

## 一、这套系统能做什么

- 读取问卷平台导出的累计报名 XLSX，不要求“序号”连续。
- 以学号作为报名者的唯一标识，识别新增报名、资料变更和重复提交。
- 同一学号有多份回答时采用最新提交，不会把同一个人安排两次。
- 将问卷中的具体面试时间转换成统一的场次编号。
- 保留仍然有效的既有排班，减少反复调整给报名者带来的困扰。
- 按固定优先级自动排班，重点避免只有 1～2 人的场次，目标为每场 5 人。
- 自动生成供管理层使用的本地 XLSX 排班表和 PNG 预览图。
- 自动生成本次更新的冲突报告，列出新增、变更、移动、未排上、线上选项、1～2 人场次和 6 人场次。
- 在推送前运行自动测试和数据校验；GitHub 收到更新后还会再次运行校验。
- 直接维护私有仓库的 `main` 分支，不使用 Pull Request，也不允许 force push。

## 二、2026 年面试场次

当前共配置 41 个线下面试场次，每场 30 分钟，相邻场次之间预留 10 分钟。

| 日期 | 时段 | 具体时间 | 场次数 |
| --- | --- | --- | ---: |
| 9 月 27 日 | 上午 | 10:00–10:30、10:40–11:10、11:20–11:50 | 3 |
| 9 月 27 日 | 下午 | 14:00–14:30、14:40–15:10、15:20–15:50、16:00–16:30、16:40–17:10 | 5 |
| 9 月 27 日 | 晚上 | 19:00–19:30、19:40–20:10、20:20–20:50、21:00–21:30、21:40–22:10 | 5 |
| 9 月 28 日至 9 月 30 日 | 晚上 | 每晚 19:00–19:30、19:40–20:10、20:20–20:50、21:00–21:30、21:40–22:10 | 15 |
| 10 月 7 日 | 上午、下午、晚上 | 与 9 月 27 日全天时间相同 | 13 |

10 月 7 日是**线下面试日**。问卷选项“国庆假期线上面试”不是“10 月 7 日所有场次均可”，也不会自动产生任何 10 月 7 日的可用时间。

生成的 XLSX 固定保留以下六个面试官/部门栏位，并由管理层另行填写：社长层、教育部、统战部、纵横部、青龙部、表演部。自动化只安排报名者，不安排面试官。

## 三、排班规则及优先级

下列规则按顺序执行。前面的规则优先于后面的偏好；例如，不能为了使用更早的日期而制造一个只有 1～2 人的场次。

1. 只安排报名者；同一名报名者最多出现一次。
2. 报名者只能被安排到本人明确选择的具体线下时段。
3. 已有安排只要仍在报名者的可用时间内，就尽量保留原场次和座位号。因可用时间改变或确有必要改善分组而移动时，必须写入冲突报告。
4. 首先尽可能让所有具有具体线下可用时间的报名者都排上。
5. 强烈避免只有 1 人或 2 人的场次；系统会优先尝试合并小组或从其他兼容场次调人。
6. 每场目标人数为 5 人。3 人或 4 人可以接受；6 人可以用于避免产生 1～2 人小组，或在场次受限时容纳全部报名者。
7. 自动排班上限为 6 人，绝不自动安排 7 人及以上。所有 6 人场次都会在报告中明确说明。
8. 在分组质量相近的方案中，尽量少开上午场次。
9. 在同样不影响上述规则的方案中，优先使用较早日期。
10. 优先填满已经启用的场次，再开启新场次；同一天内尽量安排连续场次，减少面试官等待空档。

一些典型分组结果：

- 7 名时间兼容的报名者倾向分成 3 人和 4 人，而不是 5 人和 2 人。
- 11 名时间兼容的报名者可分成 5 人和 6 人，以避免出现小组人数过少。
- 12 名时间兼容的报名者可分成两个 6 人场次，而不是留下 1～2 人的小组。

“少用上午”是分组质量之后的偏好，并非禁止上午场。若上午场能够明显改善分组或让更多人排上，系统仍会使用上午场；在质量相当时，晚上或下午优先于上午，然后才比较日期早晚。

## 四、报名表如何合并

每次问卷导出的新 XLSX 都包含此前已经收集的旧数据，因此系统采用“累计快照”模式，而不是只追加最后几行。

系统只读取以下五个字段：

| 报名表字段 | 用途 | 是否写入 GitHub |
| --- | --- | --- |
| `序号` | 提交时间完全相同时的辅助排序 | 否 |
| `提交答卷时间` | 判断同一学号的哪次提交更新 | 否 |
| `1、姓名` | 排班表显示及人员识别 | 是，仅保存姓名 |
| `3、学号` | 报名者唯一标识 | 是 |
| `9、请选择你的面试时间` | 提取具体线下可用场次 | 是，仅保存标准化后的场次编号 |

合并规则如下：

1. 去除姓名和学号两端的空格，以学号归并记录。
2. 同一学号有多次提交时，优先采用提交时间最新的一行。
3. 如果提交时间相同，再比较序号；仍相同则使用源文件中靠后的行，确保每次运行结果一致。
4. 序号可以跳号或不连续，它不用于判断“是否为新人”。
5. 新快照中没有出现的历史报名者不会被自动删除，而是继续保留并在报告中提示，防止因导出范围错误而误删数据。
6. 若报名者同时选择了具体线下时段和“国庆假期线上面试”，只使用其具体线下时段进行排班。
7. 若报名者只选择“国庆假期线上面试”，状态记为 `online_only`，不会被塞入 10 月 7 日线下场次，并在报告中提示目前没有配置线上场次。
8. 如果关键列名改变、姓名或学号缺失，或出现无法识别的面试时间选项，本次更新立即停止，不会推送不确定的数据。

报名表中的其他列可以存在，但脚本不会将它们写入 CSV 或报告。

## 五、仓库保存哪些数据

### `data/applicants.csv`

这是报名者排班状态的唯一 GitHub 数据源，列名和顺序固定：

| 列名 | 含义 |
| --- | --- |
| `student_id` | 学号，也是唯一键 |
| `name` | 姓名 |
| `available_slots` | 可用场次编号，以 `\|` 分隔 |
| `assigned_slot` | 已安排的场次编号；未排上时为空 |
| `seat_no` | 本场座位序号，范围为 1～6；未排上时为空 |
| `status` | 当前状态，见下表 |

状态值：

| 状态 | 含义 |
| --- | --- |
| `scheduled` | 已安排到具体线下场次 |
| `unassigned` | 尚未排上，通常是没有可用场次或现有场次无法容纳 |
| `online_only` | 只选择了尚未配置的线上面试选项 |
| `withdrawn` | 已退出；保留记录但不参与排班 |

### 其他受版本控制的文件

- `data/slots.csv`：所有允许使用的场次、日期、时间、时段类别和显示顺序。
- `config/schedule.json`：年份、标题、部门、目标人数、人数上限和排序偏好。
- `scripts/`：导入、排班、校验和 XLSX 生成脚本。
- `tests/`：关键排班规则的自动测试。
- `.github/workflows/validate.yml`：每次推送 `main` 后执行的 GitHub Actions 校验。

### 绝不能提交到仓库的内容

- 原始报名 XLSX 或其他原始问卷文件。
- 生成的排班 XLSX、PNG 预览和本地冲突报告。
- 手机号、QQ、IP 地址、性别、专业。
- 部门志愿、表演部兼职意向、兴趣技能和自由文本回答。
- 问卷提交时间、问卷序号及其他源文件元数据。
- 临时文件、日志和本地依赖目录。

`.gitignore` 已排除 `incoming/`、`outputs/`、`reports/` 和所有 XLS/XLSX 文件，但管理者仍应在提交前核对变更内容。私有仓库也应坚持最小化原则，不应因其私有而放宽上述限制。

## 六、管理层推荐使用方法

### 每次收到新的累计报名表

1. 从问卷平台导出当前完整的 XLSX，不要只导出新增几行，也不要手工合并多个文件。
2. 把文件保存在本机。可以放入本仓库的 `incoming/`，该目录不会被 Git 跟踪。
3. 向已安装本地 `interview-scheduler` Skill 的 Codex 提供**准确的绝对路径**，并明确是否需要同步 GitHub。
4. 等待 Agent 完成同步远端、导入、排班、校验、生成文件和冲突总结。
5. 阅读冲突总结，重点确认是否有人未排上、是否移动了旧安排、是否出现 1～2 人或 6 人场次。
6. 打开本地生成的 XLSX，填写面试地点和六个部门的面试官安排。

推荐指令示例：

```text
请用 interview-scheduler 处理报名表
D:\报名表\最新累计报名.xlsx，完成排班、冲突总结、生成本地 XLSX，并同步到 GitHub main。
```

如果只想查看结果、不希望修改 GitHub，应明确说明：

```text
请用 interview-scheduler 处理这份报名表并生成本地预览，但不要推送 GitHub。
```

只有当前请求明确包含“同步”“上传”“发布”或“完成完整更新流程”时，Agent 才会向 GitHub 写入。

### Agent 执行的标准流程

1. 检查本地工作区，确认不存在来源不明的未提交修改。
2. 切换到 `main`，从 `origin/main` 获取最新版本，并只允许 fast-forward 更新。
3. 读取指定 XLSX，按学号和最新提交时间更新 `data/applicants.csv`。
4. 保留有效旧安排，按本 README 的优先级处理新增人员和冲突。
5. 运行排班单元测试和数据校验。
6. 在本地生成 XLSX、PNG 预览和冲突报告，并进行视觉检查。
7. 只暂存预期的仓库文件，不使用 `git add .`，也不提交本地输出。
8. 推送前再次检查远端是否被其他成员更新。如远端发生一次并发更新，最多安全地 rebase 一次并重新运行全套流程；若出现冲突或远端再次变化，则停止并请管理层处理。
9. 将验证通过的提交直接推送到 `main`，绝不 force push。

## 七、每次更新会得到什么

以下文件只保存在运行 Agent 的本机，不会进入 GitHub：

| 文件 | 用途 |
| --- | --- |
| `outputs/2026_interview_schedule.xlsx` | 正式排班表；候选人姓名已填入，面试官栏留空 |
| `outputs/2026_interview_schedule_preview.png` | 快速检查版式和姓名位置 |
| `reports/latest-conflicts.md` | 本次导入、排班变化和例外情况的详细报告 |

冲突报告会列出：

- 原始有效行数及按学号归并后的人数。
- 新增、信息或可用时间发生变化、重复提交的报名者。
- 新快照中未出现但被保留的历史报名者。
- 被移动的既有安排及移动前后的场次。
- 尚未排上的报名者和只选择线上面试的报名者。
- 无法消除的 1～2 人场次。
- 为避免小组过小或容纳报名者而使用的 6 人场次。

1～2 人场次和 6 人场次属于必须显著报告的例外，但不会自动阻止发布；关键数据错误、7 人及以上场次、测试失败或 Git 冲突会阻止发布。

## 八、技术维护命令

本项目面向已配置好工作区依赖的 Codex 本地环境，XLSX 导入和生成依赖该环境提供的 `@oai/artifact-tool`。普通成员通常无需直接运行命令。

```powershell
# 处理一份新的累计报名表，同时更新 CSV、生成 XLSX/预览和报告
node scripts/update-schedule.mjs --input "D:\报名表\最新累计报名.xlsx"

# 运行排班规则测试
npm test

# 校验 CSV 结构、场次、可用时间、座位号和人数上限
npm run validate

# 不导入报名表，只根据当前 CSV 重新生成本地 XLSX
npm run build
```

每次向 `main` 推送后，GitHub Actions 会自动执行 `npm test` 和 `npm run validate`。Actions 通过只说明仓库中的结构化数据有效；生成的 XLSX 不上传，因此仍需在本地进行视觉检查。

## 九、哪些情况需要人工确认

出现以下情况时不要绕过校验或手工强推：

- 问卷关键列名或面试选项发生变化，脚本无法识别。
- 报名者没有姓名或学号。
- 某人没有任何可识别的具体线下时间。
- 仍然存在无法合并的 1～2 人小组。
- 为排下所有人使用了 6 人场次。
- 原有安排因新提交或分组优化而发生移动。
- 新导出的累计表意外缺少一批历史报名者。
- 本地与远端存在无法自动解决的 Git 冲突。

对排班进行人工调整时，应修改结构化数据后重新生成 XLSX，而不要把 XLSX 当作数据源直接维护。这样才能保证下一次导入、校验和多人协作继续有效。

## 十、常见问题

### 为什么不直接维护 XLSX？

XLSX 适合查看和打印，但不适合多人比较每次修改。CSV 可以被 Git 精确追踪，脚本又能用固定版式随时重新生成 XLSX，因此结构化 CSV 才是正式数据源。

### 同一个人重新提交问卷会怎样？

系统按学号认人，只采用最新提交的姓名和可用时间。若原安排不再可用会重新排班；仍然有效时尽量保留。

### 新报名表里没有某个旧报名者，会被删除吗？

不会。系统默认这是导出范围可能不完整，先保留旧记录并在报告中提示。删除或标记退出需要明确的人工决定。

### 为什么有时会出现 6 人场？

6 人不是默认目标。它只在避免 1～2 人小组、减少无法排班人数或场次受到限制时使用，而且必须在报告中说明。

### “国庆假期线上面试”为什么没有排到 10 月 7 日？

因为该问卷选项只表达线上意向，而 10 月 7 日配置的是线下面试。两者没有自动映射关系。

### 可以直接修改生成的 XLSX 吗？

可以临时填写地点和面试官，但不要把其中的候选人改动视为正式排班修改。候选人安排应回到 CSV 或报名数据中处理，再重新生成 XLSX，否则下次运行会覆盖这些手工改动。
